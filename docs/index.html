StokEngineer

An open DFS projection, ownership, lineup-optimisation and contest-simulation engine for DraftKings and FanDuel — built only on free, publicly available data: no subscriptions, no trials, no paid feeds, no manual data entry. Every number on this page comes from the source registry, the claim ledger, or a real run of the engine, and every assumption is labelled as an assumption.

What it does

Projections

Per-sport stat-line simulation scored with the site's own published table: projection, ceiling (75th percentile), floor (25th), standard deviation, boom %, bust %, value, points per dollar. Basketball is minutes-first, as the published methodology says; baseball is a multinomial over plate appearances with team run environment; football is volume × efficiency with shared team latents.

Ownership

A simulated field, priced from documented features and simulated to projected ownership. Labelled a simulated-field estimate everywhere, never "observed ownership" — the engine cannot see real ownership unless you import your own contest results CSV.

Lineup optimisation

Exact mixed-integer solve (pulp/CBC) with explicit slot-assignment variables, plus a branch-and-bound fallback when no solver is installed. Locks, exposures, multi-entry uniqueness, stacks and bring-backs, MLB hitter caps and the multi-game rule are all enforced, and every line is re-checked with the same validator the rules module exposes.

Contest simulation

A simulated field, real ranks (1 + number of strictly better scores), a payout table and per-lineup ROI, cash rate, top-1% rate and percentiles. Payouts are meant to come from your own contest via CSV; the built-in curves are labelled illustrative and the engine prints a warning when ROI looks arithmetically implausible.

Quick start

pip install -r requirements.txt
python -m src.stokengineer.cli doctor          # dependencies, hosts actually reachable, registry
python -m src.stokengineer.cli project  --sample sample_nfl_dk.json
python -m src.stokengineer.cli ownership --sample sample_nfl_dk.json
python -m src.stokengineer.cli optimize --sample sample_nfl_dk.json --n-lineups 3 --projection-error 0.25
python -m src.stokengineer.cli simulate --sample sample_nfl_dk.json --field-size 600
python -m src.stokengineer.cli forward-test --sport mlb --date 2026-09-21   # free official MLB data
python -m src.stokengineer.cli verify
Synthetic inputs. The bundled slates are deterministic fixtures, not real salaries or real players. They are labelled "synthetic": true in the file, in every report built from them, and on this page. Real slates come from your own JSON/CSV export or from the free ingestion helpers.

How it works

  1. Rules first. One module owns legality and scoring; the optimiser and the validator cannot disagree, because validation runs on every optimiser result and raises if it ever does.
  2. Stat lines, not point guesses. Each sport is simulated at the level of the stats the sites actually pay for, then scored with the official table — so a rule change is a data change, not a code change.
  3. Correlation is structural, then calibrated. Teammates share team latents, and a documented calibration reshapes variance into a shared team component plus a private one while preserving each player's mean and standard deviation exactly — ceilings and boom rates stay put, the joint structure is what changes.
  4. Honest testing. The MLB forward test rebuilds every input from season totals minus the game being predicted, because a season average that already contains the game is a leak, not a test.
  5. Provenance everywhere. Reports carry the command, timestamp, environment and a SHA-256 of the payload; source ids are validated on load and unknown ids raise.

    Limitations

    Rendered from LIMITATIONS.md at build time, so the site cannot quietly drop the uncomfortable parts. The headline one: simulated ROI is not a forecast — it is dominated by the assumed field behaviour, and the engine says so next to every ROI it prints.

    Next steps

    Make ROI trustworthy

    • Calibrate the field model (feature weights, sharp share, player exposure) against real free ownership exports from a user's own contest results.
    • Model entrants as a distribution over strategies instead of one noisy view per entry.
    • Import real payout tables through PayoutStructure.from_csv and publish the ROI distribution, not a single number.

    Make the models measurable

    • Run the MLB forward test on a schedule in CI and commit the reports (the harness exists, this sandbox has no egress to MLB).
    • Wire SimulationConfig.from_history to nflverse / nba_api / MLB StatsAPI logs so dispersions are fitted instead of assumed.
    • Backtest ownership against real contest ownership; report calibration curves.

    Broaden coverage

    • NFL and NBA forward tests and sample slates (MLB is done first because its official data is the easiest to verify).
    • NHL projection model (rules are already transcribed and enforced).
    • Late swap and showdown/single-game formats.

    Keep the sources honest

    • Re-fetch the 11 carried-over sources and either verify or drop them.
    • Re-run tools/check_links.py in CI on every change.
    • Replace third-party FanDuel roster values the moment FanDuel publishes them.
