# StokEngineer

An open, source-verified DFS **projection, ownership, lineup-optimisation and contest-simulation
engine** for DraftKings and FanDuel, built to work on **free, publicly available data** only —
no subscriptions, no trials, no paid feeds, no manual data entry.

Everything this repository asserts is either (a) quoted against a source a human can open and
re-check (`src/data/sources_verified.json`), or (b) labelled as an assumption with the number and
where it came from (`src/data/claims.json`, `LIMITATIONS.md`). Nothing is asserted loosely.

* Site: https://buffedlizard55-lab.github.io/StokEngineer/ (built from `docs/`, regenerated by
  `python tools/build_site_data.py`)
* Engine package: `src/stokengineer/`
* Rules the engine enforces are transcribed from the sites' own rule pages, per sport, with the
  URL recorded next to each number (`src/data/roster_rules.json`, `src/data/scoring_rules.json`).

## What it does

| Command | What it produces |
| --- | --- |
| `doctor` | environment, dependencies, which data hosts are actually reachable, registry/claim checks |
| `rules --site X --sport Y` | the verified roster + scoring rules, with the source id |
| `project --slate file.json` | projections, ceiling (75th pct), floor (25th pct), std dev, boom %, bust %, value, points-per-$ |
| `ownership --slate file.json` | projected ownership from a simulated field (labelled an estimate, never "observed") |
| `optimize --slate file.json` | legal lineups: exact solver (pulp/CBC) with a documented DFS fallback, exposure caps, stacks and bring-backs |
| `simulate --slate file.json` | full slate run: projections → ownership → lineups → contest simulation with ranks, cash rate, ROI |
| `backtest --predictions p.json --actuals a.csv` | accuracy metrics (MAE, RMSE, bias, Spearman, R², top-N overlap, boom Brier score) |
| `forward-test --sport mlb --date YYYY-MM-DD` | a real out-of-sample accuracy test on completed MLB games using free official data |
| `site-data` | rebuilds the JSON/JS behind the GitHub Pages site |
| `verify` | registry, claims, rules and sample integrity |

```bash
pip install numpy pulp       # numpy is required; pulp enables the exact solver
python -m src.stokengineer.cli doctor
python -m src.stokengineer.cli project  --sample sample_nfl_dk.json
python -m src.stokengineer.cli optimize --sample sample_nfl_dk.json --n-lineups 3
python -m src.stokengineer.cli simulate --sample sample_nfl_dk.json --field-size 600
python -m src.stokengineer.cli forward-test --sport mlb --date 2026-09-21   # needs network
```

The bundled slates in `src/data/samples/` are **synthetic fixtures**, regenerated by
`python tools/make_sample_data.py` and labelled `"synthetic": true` in the file, in every report
built from them and on the site. They exist so the engine, the tests and the site can run with no
network. They are not real salaries and never describe real players.

## Bring your own data (free)

The engine never needs a paid feed. It reads:

* a **slate JSON** (`--slate`) with `id`, `name`, `team`, `opponent`, `positions`, `salary`,
  `game_id` and a `props` block (the model inputs — per-stat rates/volumes; see any sample file
  for the exact keys per sport);
* **CSV imports** (`src/stokengineer/ingest.py`): `import_projections_csv`, `import_actuals_csv`,
  `import_ownership_csv`, and `PayoutStructure.from_csv` for a real contest payout table;
* **free live sources** (all keyless, listed below), used by `forward-test` and the ingestion
  helpers: MLB StatsAPI, ESPN's public scoreboard, nflverse releases, `nba_api`.

## How the engine works

1. **Rules first.** `rules.py` loads the transcribed roster/scoring rules and is the single source
   of truth for legality and scoring. `validate_lineup` uses exact bipartite matching (Kuhn) to
   decide whether a set of players can fill the slots at all, so "legal" is not a heuristic.
2. **Stat-line simulation.** `models.py` simulates *stat lines* per sport (multinomial plate
   appearances, Poisson counts from rates, player minutes, team volume/scoring latents) and then
   scores them with the official table for the site in question. Marginals give projection,
   ceiling, floor, boom % and bust %.
3. **Correlation.** Teammates share team latents, and `apply_teammate_correlation` re-shapes the
   variance into a shared team component plus a private one at a documented target correlation
   (default 0.12 → measured ≈ 0.36 within team). Marginals are preserved exactly, so ceilings and
   boom rates do not move — only the joint structure, which is what a stack is betting on.
4. **Ownership.** `ownership.py` prices a field from documented features and simulates that field
   to get projected ownership. Every report labels it a *simulated-field estimate*, and the labels
   are never presented as observed ownership.
5. **Optimisation.** `optimizer.py` solves the lineup with an exact MILP (pulp/CBC, open source)
   using explicit slot-assignment variables, and falls back to a branch-and-bound DFS with an
   admissible bound when no solver is present. Both paths validate their output with the same
   validator the rules use. Objective modes: median, ceiling, floor, and a risk-adjusted surrogate.
6. **Contest simulation.** `simulate.py` builds a field, ranks the user's lineups among it
   (rank = 1 + number of strictly better field scores), maps ranks to a payout table and reports
   ROI, cash rate, top-1% rate and percentiles. Payouts must come from the user's real contest
   (`PayoutStructure.from_csv`); the built-in `illustrative_*` curves exist only to exercise the
   machinery and are labelled as illustrative everywhere they appear.

## Honesty rules this repository follows

* A number that comes from a source carries the source id; a number that is an assumption says so.
* `Registry.validate()` refuses unknown source ids, and `verify` fails if any claim cites a source
  that is not declared.
* Reports are wrapped by `provenance.write_json_with_provenance` with the command, timestamp,
  environment and a SHA-256 of the payload, so any published number can be traced to the run that
  produced it.
* Where a paid product's internals are not knowable (Stokastic's weights, sigmas and ownership
  coefficients — claim `c24`), no guess is presented as fact.
* Where free data is incomplete for a test (salaries on the MLB box-score path), the test reports
  **only** what it can support and says so.

See `LIMITATIONS.md` for what is not trustworthy yet, `PASSES.md` for the three-pass build log and
`VERIFICATION.md` for how each claim was checked and which irregularities are flagged for review.
